# Database Schema Guidelines

## Purpose

Provide concise, actionable rules for the agent when proposing or making database schema changes. Always prioritize performance, security, and non-redundant relationships.

## When to apply

Use this skill when the user asks the agent to:
- create, modify, or remove tables, columns, constraints, or relationships
- add or adjust indexes, ownership, or foreign keys
- touch the database structure in any way

## Core rules (strict)

1. Edit ONLY the schema files inside `server/db/schema/`. The agent must make changes **exclusively** in that folder.
2. NEVER edit any file inside `server/db/migrations/`. Migration files must be generated by the Drizzle CLI—do not modify or create migration files by hand.
3. After completing schema edits, instruct the user to run these commands manually, in this exact order:
   - `pnpm drizzle-kit generate` (generates new migration files)
   - `pnpm drizzle-kit migrate` (runs the generated migrations)

## Performance guidance

- Add indexes for columns that will be frequently used in WHERE filters, JOINs, or ORDER BY. Create non-unique indexes explicitly — do not create duplicate indexes for columns already indexed.
- Do NOT add indexes for columns that are rarely filtered or that have extremely high cardinality without measured need.
- Prefer composite indexes that match common query patterns (e.g., (user_id, created_at) for queries filtering by user and ordering by date).
- Consider column types and sizes: choose the smallest appropriate type to reduce storage and improve cache efficiency.

## Security & constraints

- Enforce NOT NULL and appropriate data types for critical fields.
- Use foreign key constraints to maintain referential integrity; prefer ON DELETE/UPDATE policies that match business rules (restrict, cascade, set null) and document the decision.
- Avoid storing sensitive data in plaintext columns. Recommend encryption or separate secure storage for secrets and PII.
- Validate assumptions about maximum lengths, enum values, and value ranges at the schema level when feasible.

## Ownership & multi-tenant patterns

- Explicitly model ownership when records belong to a user, organization, or tenant (e.g., `owner_id`, `organization_id` with FK).
- Add indexes on ownership columns that are commonly used for filtering.
- For multi-tenant setups, prefer schema or tenant_id patterns consistent with the project's established approach; do not introduce ad-hoc tenant solutions.

## Relationships & redundancy

- Model relationships with normalized foreign keys; avoid duplicating data across tables.
- Denormalize only when there's a proven performance need and document the trade-offs.
- Use junction tables for many-to-many relationships; index foreign keys on the junction table.
- Ensure one canonical source of truth for each piece of data.

## Naming conventions & documentation

- Follow existing project naming conventions for tables, columns, and indexes.
- Name indexes and foreign keys clearly (e.g., `idx_orders_customer_id`, `fk_orders_customer_id`).
- Add short comments in the schema describing non-obvious decisions (composite index rationale, cascade behavior).

## Example checklist for a schema change

- [ ] Modify only files under `server/db/schema/`
- [ ] Add indexes for frequently filtered columns (non-unique)
- [ ] Model ownership with FKs and indexes where needed
- [ ] Use FK constraints with appropriate ON DELETE/UPDATE actions
- [ ] Avoid redundant columns; document denormalization if used
- [ ] Keep schema changes minimal and focused
- [ ] Tell the user to run Drizzle CLI commands manually (see below)

## Final user instruction (must be shown every time)

After the agent edits schema files under `server/db/schema/`, prompt the user to run these commands manually—in this exact order:

1. `pnpm drizzle-kit generate`  # generates migration files from schema changes
2. `pnpm drizzle-kit migrate`   # runs the generated migrations

Do NOT attempt to run these commands automatically. The user must execute them locally.

## Short examples

### Good: add index for filter column
Modify `server/db/schema/posts.ts` to add an index on `author_id` (non-unique) if queries frequently filter by `author_id`.

### Bad: editing migrations
Do not open or change `server/db/migrations/*` — these files should only be produced by `drizzle-kit generate`.

## Troubleshooting hints

- If a migration is missing fields or has unexpected behavior, revert schema edits, discuss the desired change, and re-apply carefully before running the Drizzle CLI.
- If unsure about cascade rules or ownership semantics, ask the user for the expected business behavior before changing constraints.
